# PostProduction Planner | Тестовое задание для "Красный Квадрат"

## Описание проекта

PostProduction Planner — модуль системы планирования отдела постпродакшн, разработанный для управления задачами (tasks). Интерфейс позволяет менеджерам планировать работы, а исполнителям — отслеживать назначенные задачи.

## Бизнес-контекст

- Задачи привязаны к проектам и производственным объектам
- Типы работ: монтаж, цветокоррекция, графика, звук
- Назначение одному или нескольким исполнителям
- Учет плановых и фактических часов
- Статусы: не начата, в работе, на паузе, завершена

## Основной функционал

- ✅ Просмотр списка задач в виде таблицы с сортировкой
- ✅ Фильтрация по статусу, типу работы, исполнителю
- ✅ Поиск по названию задачи
- ✅ CRUD операции (создание, редактирование, удаление)
- ✅ Изменение статуса через drag & drop в таблице и канбан-доске
- ✅ Пагинация и синхронизация с URL параметрами

## Ключевые архитектурные решения

1. **Композаблы для бизнес-логики.**
   Вынесение логики в composables позволяет переиспользовать код между таблицей и канбан-доской, а также упрощает тестирование.

2. **Нормализация данных в store.**
   Хранение задач в нормализованном виде с индексацией по ID для быстрого доступа и обновления.

3. **URL-синхронизация и настраиваемая пагинация.**
   Состояние пагинации (page, limit) синхронизируется с URL-параметрами, что позволяет сохранять состояние при перезагрузке и делиться ссылками.

4. **Delta-обновления для порядка задач.**
   Вместо отправки всего массиса при перетаскивании отправляется только дельта изменений ([{ id, order }]), что значительно уменьшает нагрузку на сервер при 1000+ задачах.

## API Endpoints

Базовый URL: http://localhost:3000/api

### Параметры запросов с пагинацией

| Параметр | Тип    | Описание                         | Пример     |
| -------- | ------ | -------------------------------- | ---------- |
| `_page`  | number | Номер страницы (начиная с 1)     | `page=1`   |
| `_limit` | number | Количество элементов на странице | `limit=50` |

Примеры запроса с пагинацией:

```javascript
// Вторая страница по 20 записей
GET /api/tasks?\_page=2&\_limit=20
// Первая страница с 1000 записей
GET /api/tasks?\_limit=1000

// Формат ответа с пагинацией
{
   "data": Task[], // Массив задач на текущей странице
   "pageData": {
      "page": number, // Текущая страница
      "limit": number, // Лимит на страницу
      "total": number, // Общее количество страниц
      "next": boolean, // Есть ли следующая страница
      "prev": boolean, // Есть ли предыдущая страница
      "totalEntries": number // Всего записей в коллекции
   }
}
```

### Доступные endpoints

#### Задачи (Tasks)

| Метод  | Endpoint         | Описание                           | Тело запроса                    | Ответ                                      |
| ------ | ---------------- | ---------------------------------- | ------------------------------- | ------------------------------------------ |
| GET    | `/tasks`         | Получить список задач с пагинацией | Query params: `_page`, `_limit` | `{ data: Task[], pageData: PageDataType }` |
| GET    | `/tasks/:id`     | Получить задачу по ID              | -                               | `Task`                                     |
| POST   | `/tasks`         | Создать новую задачу               | `Omit<Task, 'id'>`              | `Task`                                     |
| PATCH  | `/tasks/:id`     | Частично обновить задачу           | `Partial<Task>`                 | `Task`                                     |
| DELETE | `/tasks/:id`     | Удалить задачу                     | -                               | `void`                                     |
| PATCH  | `/tasks/order`   | Обновить порядок задач (delta)     | `{ orders: OrderDeltaItem[] }`  | `void`                                     |
| GET    | `/filters`       | Получить текущие фильтры           | -                               | `TaskFiltersType`                          |
| PUT    | `/filters/apply` | Применить новые фильтры            | `Partial<TaskFiltersType>`      | `TaskFiltersType`                          |

#### Фильтры (Filters)

| Метод | Endpoint         | Описание                 | Тело запроса               | Ответ             |
| ----- | ---------------- | ------------------------ | -------------------------- | ----------------- |
| GET   | `/filters`       | Получить текущие фильтры | -                          | `TaskFiltersType` |
| GET   | `/filters/apply` | Применить новые фильтры  | `Partial<TaskFiltersType>` | `TaskFiltersType` |

## Ответы на организационные вопросы

1. **Как бы вы организовали разработку этого модуля в команде разработчиков, включая backend?**

   В первую очередь, познакомлюсь с командой и спецификой проекта в первые дни и исходя из этого буду планировать следующие шаги. Из общения с командой я пойму уровень компетенций каждого фронтендера, и каким образом будем взаимодействовать с бэкендом, дизайнерами. Из специфики проекта я пойму объем работ, который предстоит, конкретно какие задачи в какие сроки нужно выполнить, и как будет развиваться проект в ближайшие месяцы.

   Я вижу три первоочередные задачи, которые мне нужно будет решить:
   1. Организация командной frontend-разработки (код ревью, стендапы, единые стандарты кода, ведение гайдлайна)
   2. Настройка архитектуры приложения (об этом в следующем вопросе)
   3. Определить список и порядок выполнения задач, который минимизирует риски для бизнеса и команды, не нарушая обязательств.

   Я бы организовала таким образом:
   1. **Определю в команде ритуалы взаимодействия:** с фронтендерами устроим ежедневные 10-минутные стендапы для обсуждения прогресса в разработке и практику код ревью (с чек-листами проверки). С бэкендерами и дизайнерами договариваемся о том, как будем узнавать о готовности и изменениях в API и макетах. Договариваемся, что бэкенд нам предоставляет готовое API к моменту готовности базовых компонентов; дизайнер предоставит нам макеты к моменту готовности инфраструктуры проекта. С руководителем обговариваю ИИ-инструменты, которые можем использовать для работы, и при каких условиях.
   2. **Настраиваю инфраструктуру проекта, подготавливаю гайдлайн и единые стандарты кода для команды.**
   3. **Помогаю команде с установкой и настройкой проекта и интеграцией ИИ-инструментов** (если нам их разрешили и согласовали). **Фиксируем правила вдумчивого использования ИИ-инструментов в команде:** для рутины, решения ошибок и совместимости, но не для всего. **Обговариваем действия при возникновении проблем с разработкой в команде**: оповещаем ответственных лиц и совместно решаем проблему.
   4. **Определяю список и порядок задач согласно приоритету с детальной декомпозицией.** Провожу оценку влияния и усилий, оценив время выполнения каждой задачи и возможные последствия; приоритетные задачи нужно выполнять в первую очередь.
   5. **Назначаю задачи исполнителям с учетом приоритета и срочности задач, а также компетенций каждого** на основе анализа сильных сторон команды и знания системы (задачи от простого к сложному).
      Командная параллельная разработка дизайн-системы будет быстрее, если грамотно организовать, декомпозировать и назначить задачи, с учетом компетенций и знаний системы каждым участником. При этом параллелизм разработки будет более успешен, если задачи коллег не зависят друг от друга.
   6. В первую очередь будем с командой **разрабатывать базовые компоненты дизайн-системы**. К примеру, можно запараллелить разработку кнопок, полей, тултипов, попапов без ожидания выполнения этих задач другими. К моменту начала разработки макеты дизайнеров должны быть уже готовы. Делаем от простого к сложному; сложные компоненты разрабатываю с сильными разработчиками. Может понадобиться написание тестов к каждому компоненту с написанием четких use-кейсов по ТЗ. Компонент сливается в общую ветку разработки UI только после исправления всех багов и замечаний код ревью.
   7. **Настройка сторибука для проверки дизайнера и знакомства фронтендеров с дизайн-системой** (если необходимо). Тестирование базовых компонентов в ветке UI.
   8. **Разработка первых страниц:** задачи в разных режимах отображения, с фильтрами и пагинацией; страница авторизации и т.д. К началу разработки должны быть готовы и протестированы все базовые компоненты, а бэкендеры должны предоставить готовое API для первых страниц. В команде можно запараллелить разработку разных частей страниц: один разрабатывает табличные списки задач, другой канбан-доску задач, третий занимается разработкой попапа создания/редактирования формы, четвертый занимается фильтрами и пагинацией, пятый - страницей авторизации и так далее. На этом этапе желательно сохранять скорость разработки, распределяя задачи с учетом их непересекаемости и автономности от других задач. Каждая такая задача будет хорошо декомпозирована и содержит множество подзадач, минимизируя тем самым риск задержки выполнения задачи. Задача считается готовой, если все ее подзадачи выполнены, ошибки устранены, нет замечаний код ревью и т.д. По каждой подзадаче после код ревью изменения сливаются в общую ветку задачи, которая затем тестируется на стенде, устраняются дефекты, и при готовности ветка сливается в ветку релиза.
   9. В процессе разработки со временем код может усложняться, и **по моей инициативе будет приниматься решение о рефакторинге в случае, если:** код становится слишком запутанным, разрастается на множество строк, дублируется, обнаруживаются костыли или возникает множество связанных закономерных ошибок или ухудшается производительность (перерендеры или долгий рендер, долгая обработка запросов, утечки памяти в браузере). **Будем документировать код для упрошения поддержки и адаптации.** Также поощряю идейность и инициативу участников команды, будем брать во внимание то, что можно улучшить, ускорить и по возможности воплощать.

   10. **Решение конфликтных и внеплановых ситуаций.**
       - При возникновении проблем со сроками возникновения задач: Если понимаю, что не успеваем в сроки разработки в релиз, заранее оповещаю руководителя и продакт-менеджера, даю обратную связь по нашей ситуации с объяснением имеющихся проблем и причин неуспевания, предоставляю пересмотренный план с новыми сроками или вариантами решения задачи. На основе согласованного решения перераспределяю задачи в команде, оповещаю об изменениях.
       - При возникновении конфликтов в команде действую так: организую созвон в команде с участниками конфликта, гды мы конструктивно и аргументированно общаемся. Если я понимаю, как в текущей ситуации решить конфликт с учетом успевания по срокам и качественного выполнения, мы останавливаемся на единственном решении; если конфликт не получается решить технически или по разным причинам, вовлекаем руководителя и остальную часть команды, ориентируясь на приоритеты, сроки, контекст, стек и компетенции. При решении конфликта может понадобиться парное программирование или переназначение задачи другому исполнителю или перенос части задачи на новый спринт, в зависимости от ситуации.

При использовании ИИ нужно проводить более тщательное длительное код-ревью с подробным тестированием интерфейса и сверкой с ТЗ.

3. **Какие код-ревью проверки вы бы внедрили для этого модуля?**

- Следует внедрить и вести **строгую типизацию на проекте** (через strict: true в tsconfig.json) с подробным описанием сущностей, **исключив антипаттерны:** any и non-nullable операторы, чрезмерного использования необязательных опциональных полей, over-engineering с дженериками и прочим.
- **Соответствие архитектуре приложения (Composition API):** логика в store/composables, разбивка переиспользуемого кода на компоненты и модули, избегать prop drilling на 2-3 уровне вложенности и использования глобальных переменных.
- Проектировать приложение **с соблюдением принципов SOLID** (единой ответственности, открытости-закрытости и т.д.), **код-маркеров качества: DRY, KISS, YAGNI.** **Избегать антипаттернов:** нечитаемый spagetti-код, программирование методом copy-paste, магические числа и строки, God object, мёртвый код, дублирование кода и т.д.
- **Понятный нейминг** переменных, функций, классов, компонентов, композаблов.
- **Правильное использование реактивности** через: ref, reactive, computed, watch, watchEffect, shallowRef, shallowReactive.
- **Обрабатывать ошибки** через try/catch, через Sentry; отображать пользователю состояния загрузки и ошибки, предоставлять возможность отмены запроса; устранять ошибки при сборке приложения.
- **Желателен поход к написанию кода с точки зрения производительности и простоты алгоритмов**, т.е. понимать, какие методы JS/TS лучше применять по ситуации. К примеру, for() и Map быстрее работают с коллекциями, чем .forEach, и при переборе больших списков это может быть критичнее. Применять мемоизацию там, где нужно и т.д.
- **Покрытие критических функций тестами**. В зависимости от специфики проекта может понадобиться более полное покрытие тестами (юнит, е2е, интеграционные). В таком случае будет реализован автозапуск тестов и линтеров при сборке проекта.
- **Ввести практику документирования кода** для упрощения поддержки проекта в будущем и адаптации новых сотрудников.

4. **Как бы вы подошли к оптимизации производительности этого интерфейса при 1000+ задач?**

   Я бы улучшила оптимизацию производительности на фронте посредством использования:
   - **пагинации** (реализовано) или **ленивой загрузке списка методом скролла с throttling** с ограничем количества записей на странице до 20-50,
   - **виртуализации списка при 100+ записей на странице** (в планах реализовать),
   - **ленивого поиска с debounce**,
   - **ленивой загрузки компонентов** (code splitting),
   - **мемоизации вычислений через computed**,
   - **мемоизации поддерева DOM с помощью v-memo, keep-alive** (по ситуации)
   - **ленивых запросов к серверу и отмены лишних запросов через AbortController**
   - **Web Worker или IndexedDB** для тяжелых вычислений и оффлайн-работы приложения.

   Изменение порядка элементов списка с помощью **drag-and-drop** лучше реализовать **через delta order** (дельту изменений), т.е. вместо передачи на бэк полного обновленного списка передаем точечно то, что изменилось, к примеру данные в формате [{id: 1, order: 1}, {id: 2, order: 2}], и по этой дельте обновляем параметр order у каждого элемента списка, впоследствии бэк отдает сортированный список.
